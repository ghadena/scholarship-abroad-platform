### 1.4 `scripts/bulk_import.py` — Major overhaul

This was the largest change. All three import functions were reworked.

#### Student import (`import_students`)
- **NID duplicates are now flagged, not silently skipped.** If the same NID appears more than once in the source file, both rows get `duplicate_flag=1` and a `duplicate_reason` explaining which row number was the first occurrence.
- **`ON CONFLICT (national_id)` now flags instead of doing nothing:**
  ```sql
  ON CONFLICT (national_id) DO UPDATE SET
      duplicate_flag   = 1,
      duplicate_reason = EXCLUDED.duplicate_reason
  ```
- **Student_id conflicts get a `?` appended** and are flagged:
  ```python
  if existing_sid and existing_sid[0] != nid:
      sid = f"{sid}?"
      dup_flag = 1
      conflict_note = f"student_id conflict (original taken by {existing_sid[0]})"
  ```
  Any student with `student_id LIKE '%?'` needs manual review. The data quality report (Sheet 2) catches these.
- **Return signature changed** to include a `flagged` counter:
  ```python
  return inserted, flagged, skipped, nid_to_id
  ```
- **`main()` updated** accordingly: `s_ins, s_flag, s_skip, _ = import_students(...)`

#### Family import (`import_family`)
- Unrecognised relationship strings now map to `'Unknown'` instead of `'Sibling'`.
- Only `"student"` / `"موفد"` (the student themselves) cause a row to be skipped entirely (return `None` from `map_relationship`).
- `map_relationship` logic:
  ```python
  def map_relationship(raw) -> str | None:
      if not raw:
          return "Unknown"
      key = str(raw).strip().lower()
      return RELATIONSHIP_MAP.get(key, "Unknown")
      # None means skip; "Unknown" means insert with Unknown relationship
  ```

#### Enrichment import (`import_enrichment`)
- **`remaining_study_months` is no longer imported/stored.** It is always recalculated dynamically from `end_date - today` at runtime. This means the value is always current, not stale from import time.
- The INSERT now has 9 fields (not 10):
  ```sql
  INSERT INTO student_enrichment
     (national_id, decision_no, certificate, specialization, study_country,
      start_date, end_date, duration_months, months_already_spent)
  ```
- The schema column `remaining_study_months` still exists in the DB (kept as a nullable field for any manually entered values), but `bulk_import.py` no longer writes to it.

#### `CERT_MAP` fix
Added `"specialization"` → `"Specialization"` mapping so future imports classify these students correctly.

The user's Excel file had 1,858 rows. The dashboard showed 1,822. Investigation revealed:

- 1,858 Excel rows → 1,854 unique NIDs (4 true duplicates).
- 1,854 students are in the DB.
- The dashboard excludes students where `end_date < today` — 32 students had past end dates and were filtered out from the visible count.
- **All students are in the DB.** The dashboard number is intentionally lower.

176 family members were genuinely missing (the original import had skipped them due to unrecognised relationship strings that were then mapped to `None`/skip). These were imported via `import_missing_students.py`.

## 3. Why `remaining_study_months` Is No Longer Stored

The original enrichment Excel had a `Remaining_Study_Months` column calculated at the time the file was prepared. Importing this static number meant the value went stale immediately — every passing month the stored number was increasingly wrong.

The fix: calculate it dynamically wherever it's needed:
```python
enrich_df["remaining_study_months"] = (
    (pd.to_datetime(enrich_df["end_date"]) - pd.Timestamp.today()).dt.days / 30.44
).clip(lower=0).round(0).astype(int)
```

This is done at report generation time in `report.py` and in any analytics that reference remaining months.

## 5. The Specialization Display Issue

Students with `certificate = 'Specialization'` in `student_enrichment` were displaying as "Bachelors" in the Export filter because:
1. The filter options didn't include "Specialization" → fixed in `5_Export_Report.py`
2. `CERT_MAP` in `bulk_import.py` didn't have `"specialization"` as a key → fixed for future imports

The existing DB data was already correct (52 students correctly had `certificate = 'Specialization'`). No DB update was needed.

**Important DB constraint:** `students.study_level` has `CHECK (study_level IN ('Bachelors', 'Masters', 'Doctorate', 'Certificate'))` — "Specialization" is NOT in this list. "Specialization" only lives in `student_enrichment.certificate`. The `fetch_full_students_df()` COALESCE query serves it correctly via `COALESCE(e.certificate, s.study_level) AS study_level`.

## 6. Key Invariants (Do Not Break)

| Invariant | Why it matters |
|-----------|---------------|
| `auth.py` must be imported before `database.py` on every page | `auth.py` injects `DATABASE_URL` into `os.environ`; `database.py` reads it at module import time — wrong order = silent SQLite fallback |
| Always use `fetch_full_students_df()` for analytics | Raw `fetch_students_df()` returns placeholder study data for most students |
| `remaining_study_months` is calculated dynamically, never stored by bulk_import | Stored static values go stale; dynamic calc is always current |
| Per-row SAVEPOINTs in Postgres bulk insert | Without them, one bad row aborts the entire transaction |
| `accompaniments` has no UNIQUE constraint | Re-running import without TRUNCATE creates duplicate family rows |
| `student_id LIKE '%?'` means conflict-flagged | These need human review before any downstream processing |
