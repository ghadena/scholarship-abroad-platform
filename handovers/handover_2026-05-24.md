## 1. Executive Summary

### What this project is
A web-based data management platform for a government/institutional scholarship programme that sends Libyan students abroad. It tracks students, their accompanying family members (dependants), scholarship decisions, and study metadata. It also generates executive-level PDF reports for decision makers.

### Main business objective
Provide a single source of truth for all scholarship-abroad enrolments — who is abroad, where, studying what, for how long, with how many family members — so that programme managers can make informed decisions about insurance coverage, renewals, and programme planning.

### Current status
**The platform is live and populated.** As of the last bulk import:
- **~1,822 students** in the database
- **~7,748 family members (accompaniments)**
- **~1,860 enrichment records** (detailed scholarship metadata)

The Streamlit app is deployed on Streamlit Community Cloud and connected to a Neon (serverless Postgres) database. Authentication is active. All six pages are functional.

### What is working
- Full CRUD for students and accompaniments via the Data Entry page
- Role-based access control (admin / entry roles)
- Records browsing with filters (country, study level, flagged, duplicate-flagged)
- Dashboard with Plotly charts (country distribution, study level, gender, quarterly trend)
- Executive PDF report with 6 sections: KPI banner, geographic distribution, population composition, age profile & family size, study duration & time remaining, study level & field analysis
- Export page with country + gender filters; CSV, Excel, and PDF download
- Duplicate detection (exact and soft) with admin review workflow
- Deletion request workflow (entry users request; admin approves/rejects)
- Bulk import via CLI script (`scripts/bulk_import.py`) for the three-sheet Excel format
- Libyan NID validation (gender derivation from digit 1, birth year from digits 2–5)

### What is incomplete
- **Dashboard still uses `fetch_students_df()`** (raw students table) instead of `fetch_full_students_df()` (students + enrichment merged via COALESCE). This means dashboard KPIs show placeholder values (e.g. "Bachelors", "N/A") for the ~14 students who have no enrichment match, and more importantly, **all 1,822 students show their raw `study_level`/`study_field`/`country` from the students table, not the richer enrichment data**. The fix is a one-line change in `3_Dashboard.py`.
- **`app/importer.py` is effectively orphaned.** The Import page (`4_Import.py`) was stripped of its UI in the last session. `importer.py` still exists and is tested, but no page calls it anymore. It only handles students (no family/enrichment). For bulk imports, the CLI script is the right tool. The file should either be formally deprecated or repurposed.
- **`DEPLOYMENT.md` describes SQLite deployment**, but the project has migrated to Postgres. The document has not been updated.
- **The `build_quarterly_report()` alias** in `report.py` passes an empty DataFrame for `enrich_df`, so if anything still calls the old quarterly API, the study-duration and study-level sections will be blank. The alias should be removed once callers are confirmed to have migrated.
- **No scheduled backup of Neon data.** If the Neon project is accidentally deleted or the free tier is discontinued, all data is lost.

### Biggest risks / blockers
1. **Neon free tier limits.** If the project exceeds Neon's free tier compute or storage, the app will stop working with no warning to users. The connection string is stored in Streamlit Cloud secrets — if those are lost/rotated, the app goes dark.
2. **14 students with no enrichment record.** These students will always show raw placeholder values (study_level="Bachelors", study_field="N/A", dates="2020-01-01/2026-01-01") in any view that uses `fetch_full_students_df()`. This is a source-data gap, not a code bug. The source organisation needs to supply the missing rows.
3. **`credentials.yaml` / secrets.** If the Streamlit Cloud secrets are lost, no one can log in. There is no password reset mechanism in the app.
4. **No automated tests for database or report modules.** Tests exist only for `validation.py`.

### Recommended next steps (priority order)
1. Fix `3_Dashboard.py` to use `fetch_full_students_df()` — 5-minute change.
2. Export a Neon backup (SQL dump) and store it somewhere safe — do this today.
3. Formally deprecate or remove `app/importer.py` and the orphaned tests.

## 2. Project Context

### Why this work exists
A government or institutional body sponsors Libyan students to study abroad. Each student may bring family members (spouse, children, siblings). Previously, records were managed in Excel spreadsheets with no deduplication, validation, or reporting. The platform replaces those spreadsheets with a structured database, a web UI for ongoing data entry, and automated reporting.

### Stakeholders
- **Programme manager / admin:** Needs executive reports, can approve deletions, reviews duplicate flags. Uses the Admin page and Export/Report page.
- **Data entry staff:** Enters new students as decisions are issued. Uses Data Entry and Records pages. Cannot delete records directly — must submit deletion requests.
- **Source data organisation:** Supplied the initial Excel bulk data (three sheets: student data, family data, more student data). They are the authoritative source for the 14 missing enrichment records.

### Target users
Small team: likely 1–3 admin users and a handful of data-entry users. Concurrent usage is low. The app is not public-facing.

### Business value
- Eliminates duplicate enrolments and detects existing soft duplicates
- Enforces Libyan NID format rules and flags birthday mismatches for review
- Gives programme managers an at-a-glance executive report (previously required manual Excel work)
- Provides filtered export for insurance/actuarial use (country + gender filters were the specific ask)

### Expected deliverables
The platform itself is the deliverable. There is no separate BI tool or data warehouse. The PDF report is the reporting output for decision-makers.

## 3. Current Architecture & Workflow

### High-level architecture

```
┌─────────────────────────────────────────────────────┐
│              Streamlit Community Cloud               │
│                                                      │
│  app/main.py  ──►  app/pages/1_Data_Entry.py         │
│                    app/pages/2_Records.py             │
│                    app/pages/3_Dashboard.py           │
│                    app/pages/4_Import.py              │
│                    app/pages/5_Export_Report.py       │
│                    app/pages/6_Admin.py               │
│                                                      │
│  app/auth.py        (login / role enforcement)       │
│  app/database.py    (all DB calls, dual-mode)        │
│  app/validation.py  (NID rules, form validation)     │
│  app/duplicates.py  (detection + flagging)           │
│  app/report.py      (PDF generation)                 │
└────────────────────────┬────────────────────────────┘
                         │ psycopg2 (DATABASE_URL from st.secrets)
                         ▼
              ┌──────────────────────┐
              │  Neon Postgres (cloud)│
              │  tables:             │
              │  · students          │
              │  · accompaniments    │
              │  · student_enrichment│
              │  · deletion_requests │
              └──────────────────────┘

Local dev path (when DATABASE_URL is absent):
  → SQLite at data/scholarship.db  (via _sqlite_conn())
```

### Data flow for a new student entry
1. Data-entry user logs in → `app/auth.py` verifies bcrypt hash, sets `role` in session state
2. User fills form on `1_Data_Entry.py`
3. `validation.py` checks NID format, derives gender, checks birthday/NID year match
4. On submit: `database.insert_student()` writes to `students` table, writes accompaniments to `accompaniments` table, then calls `duplicates.flag_soft_duplicates()` to rescan all records
5. If `birthday_flag=1`, a warning is shown but the record is still saved

### Data flow for the bulk historical import
```
new_excel.xlsx
  ├── sheet "student data"      → import_students()    → students table
  ├── sheet "family data"       → import_family()      → accompaniments table
  └── sheet "more student data" → import_enrichment()  → student_enrichment table

Run: DATABASE_URL="postgresql://..." python3 scripts/bulk_import.py /path/to/file.xlsx
```

### Data flow for the executive report
```
fetch_full_students_df()      ─── students LEFT JOIN student_enrichment (COALESCE)
fetch_accompaniments_df()     ─── accompaniments JOIN students
fetch_enrichment_df()         ─── student_enrichment JOIN students

          ↓ all three DataFrames passed to:
build_executive_report(students_df, family_df, enrich_df)
          ↓
Matplotlib charts → PNG bytes → embedded in ReportLab PDF
          ↓
PDF bytes returned → st.download_button
```

### Dual-mode database layer
`database.py` detects `DATABASE_URL` in the environment at import time:
```python
_USE_POSTGRES = bool(os.environ.get("DATABASE_URL", ""))
```
When `_USE_POSTGRES` is `True`, all connections use psycopg2. When `False`, they use SQLite. The `_execute()` helper swaps `?` placeholders to `%s` for Postgres automatically. This means the same SQL works in both modes with minimal overhead.

**Important:** `DATABASE_URL` is injected by `app/auth.py` from `st.secrets` at app startup, before `database.py` is imported. This is a deliberate ordering hack — if you ever split auth into a separate module that doesn't run first, the Postgres connection will break silently (falling back to SQLite).

Enriched scholarship metadata from the "more student data" Excel sheet. One row per student (linked by `national_id`).

| Column | Type | Constraints | Notes |

| `id` | SERIAL PK | | |

**How it merges with `students`:**
The canonical query in `fetch_full_students_df()` uses:
```sql
COALESCE(e.study_country, s.country_abroad)  AS country_abroad
COALESCE(e.certificate,   s.study_level)     AS study_level
COALESCE(e.specialization, s.study_field)    AS study_field
COALESCE(e.start_date,    s.start_date)      AS start_date
COALESCE(e.end_date,      s.end_date)        AS end_date
COALESCE(e.decision_no,   s.decision_no)     AS decision_no
```
Enrichment takes priority. If enrichment is NULL (no matching row, or that column is NULL), the student's raw value is used as the fallback.

## 6. Codebase / Script Breakdown

### `app/main.py` — Entry point
**Purpose:** Streamlit landing page / home screen.  
**What it does:**
1. Calls `db.init_db()` — creates all tables if they don't exist (safe to call repeatedly)
2. Runs the auth login flow
3. Shows a welcome message and a 3-metric KPI strip (total students, accompaniments, flagged records)

**Important:** This is where `init_db()` is called. If you add a new table or migration, add it here (or make `init_db()` idempotent, which it already is via `CREATE TABLE IF NOT EXISTS`).

**Known issue:** The KPI strip uses `fetch_students_df()` (raw students table), not `fetch_full_students_df()`. The "Flagged Records" count is correct; the total count is correct. No enrichment data is needed here, so this is acceptable.

---

### `app/auth.py` — Authentication
**Purpose:** Wraps `streamlit-authenticator` 0.4.x. Handles login, logout, role enforcement.

**Critical ordering behaviour:**
```python
# This block runs at module import time — before database.py loads
_db_url = st.secrets.get("DATABASE_URL")
if _db_url and not os.environ.get("DATABASE_URL"):
    os.environ["DATABASE_URL"] = _db_url
```
`auth.py` is imported first on every page. It injects `DATABASE_URL` into `os.environ` so that when `database.py` is subsequently imported, `_USE_POSTGRES` evaluates correctly. **If you change the import order on any page, Postgres connectivity will break.**

**Dev mode:** If `.streamlit/credentials.yaml` does not exist AND `st.secrets` does not contain `credentials_yaml`, the app runs as admin with username `"dev"` and no password. This is intentional for local development. **Never deploy without credentials.**

**Role system:**
- `admin` — full access to all 6 pages
- `entry` — access to pages 1–5 only (cannot reach Admin page)

**How to add a user:** Edit `credentials_yaml` in Streamlit Cloud Secrets. Format:
```yaml
credentials:
  usernames:
    new_username:
      email: user@example.com
      name: Full Name
      password: "$2b$12$..."   # bcrypt hash
      role: entry              # or: admin
cookie:
  name: scholarship_cookie
  key: <long random string>
  expiry_days: 30
```

**Generating a bcrypt hash (do NOT use streamlit-authenticator's Hasher in 0.4.x — API changed):**
```bash
python3 -c "import bcrypt; print(bcrypt.hashpw(b'yourpassword', bcrypt.gensalt()).decode())"
```

### `app/database.py` — Database layer
**Purpose:** All database I/O. Abstracts Postgres vs SQLite behind a common API.

**Key functions:**

| Function | Returns | Notes |
|----------|---------|-------|
| `init_db()` | None | Creates all tables. Safe to call on every startup. |
| `get_conn()` | context manager | Yields a connection; auto-commits or rolls back |
| `insert_student(data, accompaniments)` | int (new PK) | Inserts student + accompaniments, then rescans duplicates |
| `fetch_students_df()` | DataFrame | Raw students table. Use for admin/records pages where you want to see raw values |
| `fetch_accompaniments_df()` | DataFrame | Accompaniments joined with student name/id |
| `fetch_enrichment_df()` | DataFrame | Enrichment joined with student name/id/gender/birthday |
| `fetch_full_students_df()` | DataFrame | **Canonical view.** Students LEFT JOIN enrichment via COALESCE. Use for reports and exports |
| `delete_student(pk)` | None | Hard delete; cascades to accompaniments |
| `create_deletion_request(...)` | None | Inserts pending deletion request |
| `fetch_deletion_requests_df(status)` | DataFrame | Pass `status="pending"` or `None` for all |
| `resolve_deletion_request(id, action, reviewer)` | None | action = "approved" or "rejected" |

**Placeholder system (`_placeholder`, `_execute`, `_executemany`):**
```python
def _execute(conn, sql, params=()):
    if _USE_POSTGRES:
        sql = sql.replace("?", "%s")   # SQLite uses ?, Postgres uses %s
    cur = conn.cursor()
    cur.execute(sql, params)
    return cur
```
Always use `?` in your SQL strings. The `_execute` wrapper converts them for Postgres automatically. **Never mix `?` and `%s` in the same query.**

**Schema migration (`_ensure_columns`):**
Adds `duplicate_flag` and `duplicate_reason` columns if they're missing (legacy migration for databases created before those columns existed). This runs on every `init_db()` call. If you add new columns in future, add them here.

### `app/duplicates.py` — Duplicate detection
**Purpose:** Detect and flag records that might be duplicates.

### `scripts/bulk_import.py` — CLI bulk importer (the production tool)
**Purpose:** One-shot import of the full three-sheet Excel into Neon Postgres. This is the tool used for the historical data load and for any future batch updates.

**Usage:**


**Expected Excel sheet names (exact):** `"student data"`, `"family data"`, `"more student data"`

**What it does:**
1. Parses all three sheets
2. Calls `init_db()` to ensure schema exists
3. Opens a single DB connection; inserts students with `ON CONFLICT (national_id) DO NOTHING` (idempotent — safe to re-run)
4. Builds `sid_to_dbid` map (student_id string → db PK) for family linking
5. Inserts family members (per-row savepoints to isolate constraint errors)
6. Inserts/upserts enrichment data with `ON CONFLICT (national_id) DO UPDATE SET ...`

**Per-row savepoints (critical for Postgres):**
```python
def _pg_insert_safe(conn, sql, params):
    cur = conn.cursor()
    cur.execute("SAVEPOINT sp")
    try:
        cur.execute(sql, params)
        cur.execute("RELEASE SAVEPOINT sp")
        return cur
    except Exception as e:
        cur.execute("ROLLBACK TO SAVEPOINT sp")
        raise e
```
Without savepoints, a single constraint violation (duplicate NID, malformed value) aborts the entire transaction and no rows are inserted. The savepoint approach lets the transaction continue after isolating and skipping the bad row.

| `clean_sid(val)` | Strip `.0` suffix, return empty string for "nan"/"None" |
| `clean_date(val)` | Handle datetime, date, float(NaN), and string inputs |
| `map_relationship(raw)` | Arabic + English → enum value |

## 8. Key Decisions & Reasoning

### Why Neon (Postgres) instead of SQLite
**Decision:** Migrate from SQLite to Neon serverless Postgres.  
**Reason:** Streamlit Community Cloud's free tier has no persistent disk. SQLite data is stored in the container filesystem, which is wiped on every redeploy or container restart. The user discovered this when data entered in one session disappeared after a redeploy.  
**Alternative considered:** Supabase (similar managed Postgres, mentioned briefly).  
**Tradeoff:** Neon free tier has its own limits (compute/storage). If those are hit, the app goes dark. Supabase was not chosen — no strong reason documented, Neon was tried first and worked.

### Why `sys.path.insert(0, ...)` in every page file
**Decision:** Every page file starts with:
```python
sys.path.insert(0, str(Path(__file__).parent.parent.parent))
```
**Reason:** Streamlit's multipage routing runs each page file in its own process, with the current working directory set to the page file's directory (or sometimes the repo root, inconsistently). `from app import database` fails unless the repo root is explicitly on `sys.path`. The `parent.parent.parent` path resolves: page file → `pages/` → `app/` → repo root.  
**Alternative considered:** Using a `PYTHONPATH` environment variable or a `pyproject.toml`. The sys.path hack was simpler and avoids platform differences.

### Why `auto_hash=False` in streamlit-authenticator
**Decision:** Pass `auto_hash=False` to `stauth.Authenticate()`.  
**Reason:** `streamlit-authenticator` 0.4.x, when `auto_hash=True` (the default), re-hashes passwords that are already bcrypt-hashed, producing double-hashed passwords that never match. The stored passwords are already hashed with bcrypt (generated externally). Setting `auto_hash=False` tells the library to compare the entered password against the stored hash directly.  
**Discovery:** Login was failing with correct passwords. The `auto_hash` flag was the root cause.

### Why `build_executive_report` takes three DataFrames
**Decision:** The report function accepts `students_df`, `family_df`, and `enrich_df` as separate inputs.  
**Reason:** The Export page applies country/gender filters. The filtered DataFrames need to be passed through to the report so that a "UK only" report only shows UK students. If the function queried the database internally, it couldn't respect the user's filters.  
**Consequence:** The caller is responsible for passing consistent DataFrames (i.e. `family_df` and `enrich_df` should be pre-filtered to match the same students as `students_df`). The Export page does this correctly.

### Why COALESCE join instead of patching students table directly
**Decision:** Enrichment data overrides student data at query time via COALESCE in `fetch_full_students_df()`, rather than updating the students table in place.  
**Reason:** Keeps the two data sources separable and auditable. The students table contains what was entered via the UI or imported from "student data" sheet. The enrichment table contains the richer scholarship metadata. If enrichment data is later corrected, only `student_enrichment` needs updating; the original student record is unchanged.  
**Tradeoff:** Any query that doesn't use `fetch_full_students_df()` will see placeholder values. This has already caused confusion (Dashboard still uses raw `fetch_students_df()`).

### Why per-row savepoints in `bulk_import.py`
**Decision:** Each INSERT in the bulk import is wrapped in a Postgres SAVEPOINT.  
**Reason:** Without savepoints, the first constraint violation (e.g., duplicate `national_id`) aborts the entire transaction and no rows are inserted. With savepoints, each row failure is isolated and the import continues. In the original import run, ~10 students were skipped due to constraint violations; without savepoints, all ~1,822 would have been lost.

### Why `importer.py` still exists but is not used
**Decision:** `4_Import.py` was stripped of its UI in the last session per user request ("remove the whole of bulk import section"). `importer.py` was not deleted.  
**Reason:** The user asked to remove the UI, not the underlying module. Leaving the module preserves the tests and keeps the door open for re-adding the UI later. However, `importer.py` is SQLite-only and untested against Postgres — it is effectively dead code at this point.

### Why not update the students table directly from enrichment
**Decision:** The `bulk_import.py` script does NOT patch `students.study_level`, `students.study_field`, etc. from enrichment data.  
**Reason:** The COALESCE view already serves the authoritative merged view. Patching the students table would duplicate the enrichment data in two places and create a synchronisation problem. The trade-off is that any code that queries `students` directly (rather than via `fetch_full_students_df()`) will see raw placeholder values — which is the current Dashboard bug.

## 10. Known Issues & Debugging Notes

### Issue: Login fails with "Incorrect username or password" on correct credentials
**Root cause:** Two possible causes:
1. `auto_hash=True` (default in 0.4.x) re-hashes already-hashed passwords, so login never matches
2. Extra whitespace before the password value in `credentials.yaml` (YAML is whitespace-sensitive for string values)
**Fix:** Ensure `auto_hash=False` in `stauth.Authenticate(...)` and check for leading/trailing spaces in the YAML password string.

### Issue: `ModuleNotFoundError: No module named 'app'`
**Root cause:** Streamlit's page runner executes page files from an unpredictable working directory. `from app import database` fails if the repo root is not on `sys.path`.  
**Fix:** Every page file must have these three lines at the top:
```python
import sys
from pathlib import Path
sys.path.insert(0, str(Path(__file__).parent.parent.parent))
```
(`__file__` is inside `app/pages/`, so `parent.parent.parent` = repo root)

### Issue: `TypeError: Hasher.__init__() takes 1 positional argument but 2 were given`
**Root cause:** `streamlit-authenticator` 0.4.x changed the `Hasher` class API. The old pattern `stauth.Hasher(['password']).generate()` no longer works.  
**Fix:** Use `bcrypt` directly to generate password hashes:
```bash
python3 -c "import bcrypt; print(bcrypt.hashpw(b'yourpassword', bcrypt.gensalt()).decode())"
```

### Issue: Data disappears after Streamlit Cloud redeploy
**Root cause:** Streamlit Community Cloud free tier has no persistent disk. SQLite data lives in the container filesystem and is wiped on redeploy.  
**Fix:** Migrated to Neon Postgres (persistent). This issue no longer applies as long as `DATABASE_URL` is set in secrets.

### Issue: Bulk import transaction aborts on first constraint violation
**Root cause:** In Postgres, any unhandled exception inside a transaction sets the transaction to an aborted state. All subsequent statements fail with `ERROR: current transaction is aborted`. Without savepoints, even one duplicate NID kills the entire import.  
**Fix:** Per-row `SAVEPOINT sp` / `ROLLBACK TO SAVEPOINT sp` pattern in `_pg_insert_safe()`.

### Issue: `get_conn()` context manager not yielding correctly
**Root cause:** Early version used `yield from _pg_conn()` which is valid Python syntax but incorrect for context managers (it iterates, not delegates context management).  
**Fix:** Changed to `with _pg_conn() as conn: yield conn`.

### Issue: Student 786 showing wrong country/field/dates (the "enrichment merge" concern)
**Root cause:** The user observed that student with serial number 786 in the Excel had different data than what appeared in the database. Investigation found:
- The student in question (`national_id = 119670291604`) is **genuinely absent** from the `student_enrichment` table
- The COALESCE query correctly falls back to placeholder values when no enrichment row exists
- Serial number 786 in the enrichment sheet belongs to a **different student** (`national_id = 119920157478`)
**Conclusion:** This is a source data gap, not a code bug. The code is correct.

### Issue: Dashboard showing "Bachelors" for all study levels
**Root cause:** `3_Dashboard.py` calls `fetch_students_df()` instead of `fetch_full_students_df()`. The raw students table has placeholder `study_level="Bachelors"` for bulk-imported students.  
**Fix:** Change line 22 of `3_Dashboard.py`.  
**Status:** Not yet fixed as of this handover.

### Common pitfall: using `student.id` vs Excel "serial number"
The Excel source file has a column that appears to be a serial/row number. This is **not** the database `id`. The database auto-assigns its own sequential ID on insert. When searching for a student, always use `national_id` or `student_id`, never the Excel row number.

## 13. Recommendations for Future Improvements

### Architecture
- **Add an edit/update UI for student records.** Currently impossible via the web app. Records can only be corrected by deleting and re-entering, or via direct Neon SQL access.
- **Separate the enrichment import from `bulk_import.py`.** Create a standalone script `scripts/import_enrichment.py` that only processes the "more student data" sheet. This makes it easier to re-run enrichment updates without touching student/family data.
- **Replace the `importer.py` approach** for single-record-sheet imports with a call to the three-sheet `bulk_import.py` logic, properly parameterised. Alternatively, delete `importer.py` entirely — the use case is now covered by the Data Entry form for individual records and the CLI script for batches.

### Scalability
- **Pagination in the Records page.** `st.dataframe()` with 1,822 rows is fast enough now but will degrade. At ~10,000 rows it will become noticeably slow.
- **Duplicate detection optimisation.** `flag_soft_duplicates()` runs a full self-join on every insert. Consider an index on `lower(full_name)` and only re-scanning new records rather than the entire table.
- **Connection pooling.** Each Streamlit interaction opens and closes a psycopg2 connection. Neon's serverless connection pooler (PgBouncer) is available — enable it if connection overhead becomes a problem under concurrent usage.

### Technical debt
- `DEPLOYMENT.md` is out of date. Rewrite it to describe the current Neon + Streamlit Cloud setup.
- `README.md` still references SQLite as the primary database and the old quarterly report API.
- `app/importer.py` should be deleted or flagged as SQLite-only in its docstring.
- The `build_quarterly_report` alias in `report.py` should be removed once all callers are confirmed to use `build_executive_report`.
- `updated_at` column is never updated. Either add a trigger or remove the column.

### Security
- **No password reset mechanism.** If a user forgets their password, an admin must manually update `credentials_yaml` in Streamlit Cloud secrets with a new hash.
- **Credentials stored as plain TOML text in Streamlit secrets.** This is Streamlit's standard approach — bcrypt hashes are not plain text, so password security is maintained. However, the full credentials structure (usernames, cookie key) is visible to anyone with access to the Streamlit Cloud project.
- **No rate limiting on login.** `streamlit-authenticator` handles authentication but has no built-in brute-force protection.
- **The Neon connection string is a long-lived credential.** Consider rotating it periodically.

### UX improvements
- **Records page does not show enrichment data.** The table shows raw students values. Users looking for study field or country will see "N/A" / "Unknown". Switch to `fetch_full_students_df()`.
- **No way to search by name.** The Records page only filters by country, study level, and flag status. Adding a name search text input would significantly improve usability.
- **Data Entry page does not prevent re-entry of existing national_id.** The form will submit and the DB will reject it with a UNIQUE constraint error, which surfaces as "Database error: duplicate key...". Add a pre-check: query for existing `national_id` before attempting insert.

### Automation
- **Nightly backup.** A GitHub Actions workflow running `pg_dump` and uploading to Google Drive or S3 would eliminate the manual backup risk.
- **Data quality re-scan.** A scheduled job could re-run the duplicate flag scan weekly and email the admin if new duplicates appear.

## 14. Quick Start Guide

You are joining a live Streamlit app connected to a Postgres database. Here is the minimum you need to know to continue work tomorrow.

### The three things that will break the app if touched carelessly
